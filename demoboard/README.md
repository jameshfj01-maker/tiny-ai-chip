# 데모 보드 테스트 계획

칩이 도착하면 Tiny Tapeout 데모 보드에 꽂아서, 시뮬레이션에서 확인한 것과 똑같이 동작하는지 시험한다.
실제 칩 회사에서는 이 단계를 **실리콘 검증 (post-silicon validation)** 이라고 부른다.
시뮬레이션과 하드닝이 "설계도가 맞다" 를 확인했다면, 이 단계는 "공장에서 만든 진짜 칩이 설계도대로 나왔다" 를 확인한다.

```
  컴퓨터 ──USB──► 데모 보드의 RP2040/RP2350 (MicroPython)
                       │  ui_in[7:0]   데이터
                       │  uio[3:0]     주소
                       │  uio[4]       write
                       │  uio[5]       start
                       │  clk, rst_n
                       v
                 [ 우리 칩 tt_um_jameshfj01_tiny_ai_chip ]
                       │  uo_out[7:0]  결과 바이트
                       └► uio[7]       done
```

## 준비물

- 우리 칩이 들어 있는 Tiny Tapeout 칩 + 데모 보드
- USB 케이블, 컴퓨터
- `mpremote` (컴퓨터에서 보드로 파일을 보내는 도구): `pip install mpremote`
- 이 폴더의 `tiny_ai_chip.py`

## 시작 전 주의

- **uio[7] 은 칩이 내보내는 핀(done)이다.** 보드(Pico) 쪽에서 이 핀을 출력으로 설정하면 둘이 서로 다른 값을 내보내며 부딪칠 수 있다.
  스크립트는 `uio_oe_pico = 0x7F` 로 uio[6:0] 만 Pico 출력으로 쓰고 uio[7] 은 입력으로 둔다. 직접 REPL 에서 핀을 만질 때도 이 값을 바꾸지 않는다.
- 데모 보드의 입력 DIP 스위치는 Pico 가 ui_in 을 내보내는 동안 겹치지 않게 꺼 두는 것을 권장한다 (보드 설명서로 확인).
- SDK 설명서에 `ASIC_RP_CONTROL` 모드 설명 문장이 헷갈리게 적혀 있다. 그래서 처음에는 **수동 클럭**으로 천천히 시험해서, Pico 가 정말 ui_in 을 움직이는지부터 확인한다.

## 순서

### 1단계: 보드와 칩 확인

USB 로 연결하고 REPL 에 들어간다 (리눅스 예: `/dev/ttyACM0`, 윈도우는 COM 포트).

```bash
mpremote connect /dev/ttyACM0 repl
```

REPL 에서:

```python
from ttboard.demoboard import DemoBoard
tt = DemoBoard.get()
print(tt.shuttle)                  # 어느 셔틀 칩인지
tt.shuttle.find('tiny_ai')         # 우리 프로젝트가 목록에 있는지
```

`tt_um_jameshfj01_tiny_ai_chip` 이 보이면 다음으로 간다. (REPL 에서 나오기: Ctrl-X)

### 2단계: 스크립트 보내기

```bash
mpremote connect /dev/ttyACM0 fs cp demoboard/tiny_ai_chip.py :tiny_ai_chip.py
```

### 3단계: 수동 클럭 시험

수동 클럭은 Pico 가 클럭을 한 번씩 직접 쳐 주는 방식이다. 느리지만 시뮬레이션과 똑같이 한 클럭씩 움직여서 결과를 그대로 비교할 수 있다.

```python
import tiny_ai_chip
tiny_ai_chip.main(freqs=(None,))
```

나와야 하는 결과 (14개 전부 PASS):

| 시험 | 무엇을 보나 |
|---|---|
| 리셋 후 done = 0 | 리셋과 done 핀이 살아 있다 |
| 리셋 후 결과 = 0 | 결과 레지스터가 리셋된다, 읽기 주소가 동작한다 |
| start -> done 클럭 수 544..552 | 계산에 4 박자 x 136 클럭 = 544 클럭 + 동기화가 걸린다 |
| done 이 1 로 유지 | done 이 다음 start 까지 유지된다 |
| 알려진 예시 | [[1,2],[3,4]] x [[5,6],[7,8]] = [[19,22],[43,50]] |
| 단위행렬, 음수 섞임 | 부호 있는 계산이 맞다 |
| 끝값 3개 (-128, 127) | 17비트 결과와 3바이트 읽기가 끝값에서도 맞다 |
| 0 행렬 | 이전 결과가 남지 않는다 |
| 안 쓰는 읽기 주소 = 0 | 주소 3, 7, 11, 15 는 0 |
| A00 만 다시 쓰기 | 저장 레지스터가 값을 기억한다 |
| 무작위 20 쌍 | 위에서 못 본 조합들 |

### 4단계: 속도 올리기

수동 클럭이 다 통과하면, 클럭을 자동으로 돌리면서 주파수를 올려 본다.

```python
tiny_ai_chip.main()    # 수동, 1kHz, 100kHz, 1MHz, 10MHz, 25MHz, 50MHz 순서
```

- 하드닝의 타이밍 분석 결과는 CLAUDE.md 의 "타일 결정 기록" 에 있다. 제출하는 버전의 결과와 비교한다.
- 수동 클럭은 한 번 칠 때마다 Pico 가 파이썬 명령을 실행해서 느리다. 행렬곱 한 번에 약 550 클럭이라 시험 전체가 몇 분 걸릴 수 있다.
- 자동 클럭에서는 "start -> done 클럭 수" 를 정확히 셀 수 없어서 그 항목은 INFO 로만 나온다 (그래서 13개).
- SDK 설명서에 보드가 낼 수 있는 최대 클럭이 적혀 있지 않다. 높은 주파수에서 실패하면 칩 문제인지 보드 문제인지 먼저 구분해야 한다 (아래 문제 해결 참고).

### 5단계: 결과 기록

| 날짜 | 클럭 | 통과 / 전체 | 메모 |
|---|---|---|---|
| | 수동 | / 14 | |
| | 1 kHz | / 13 | |
| | 100 kHz | / 13 | |
| | 1 MHz | / 13 | |
| | 10 MHz | / 13 | |
| | 25 MHz | / 13 | |
| | 50 MHz | / 13 | |

결과는 이 표에 적어서 커밋해 두면, 설계 기록(타이밍 분석 결과)과 실제 칩 결과를 나란히 비교할 수 있다.

## 문제 해결

| 증상 | 먼저 볼 것 |
|---|---|
| `AttributeError` (프로젝트 이름) | 1단계의 `tt.shuttle.find(...)` 로 이름을 다시 확인한다. 셔틀에 따라 이름이 다를 수 있다 |
| 모든 결과가 0, done 이 안 옴 | 프로젝트가 켜졌는지 (`tt.shuttle.enabled`), 모드가 `ASIC_RP_CONTROL` 인지, Pico 가 ui_in 을 정말 바꾸는지 (`tt.ui_in.value` 를 바꾸며 확인) |
| "done 이 올라오지 않았다" | start 핀(uio[5])이 Pico 출력인지 (`tt.uio_oe_pico.value` 가 0x7F), 클럭이 도는지 |
| 결과가 조금씩만 틀림 | 어느 바이트가 틀리는지 본다. 위 바이트(주소 2, 6, 10, 14)만 틀리면 부호 확장, 특정 칸만 틀리면 그 MAC |
| 수동은 통과, 높은 주파수만 실패 | 실패가 시작되는 주파수를 기록한다. 보드의 Pico 가 핀을 바꾸는 속도와 `wait_clocks` 의 기다리는 시간이 충분한지도 의심한다 (스크립트는 최소 20us 씩 기다린다) |

## 이 스크립트는 어떻게 확인했나

칩이 오기 전에 스크립트가 틀리면 진짜 칩을 의심하게 되니까, 스크립트도 미리 시험했다.

- `test/demoboard/`: 같은 `tiny_ai_chip.py` 를 그대로 RTL 시뮬레이션에 연결한다 (`SimBoard` 가 데모 보드 대신 핀을 움직인다).
  전체 시험이 통과하는지, 일부러 결과 1비트를 틀리게 읽으면 실패를 잡아내는지, start 부터 done 까지 클럭 수가 맞는지 본다.
- MicroPython 1.22 (리눅스판)에서 가짜 `ttboard` 모듈로 스크립트를 실제로 실행해서, 문법과 실행이 MicroPython 에서 문제없는지 확인했다 (이 가짜 모듈은 저장소에 넣지 않았다).
